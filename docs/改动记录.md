# 改动记录（排查用）

**这份文档的用法**：动手改代码前先在这里搜一遍相关模块，看清"这里已经改过什么、为什么这么改、当时实测数字是多少"，避免把已经踩过的坑再踩一遍。每完成一个有实际影响的改动（性能、交互、数据结构、构建），在顶部追加一条。

**每条记录必须包含**：现象 → 实测数据（含测试条件与数据来源）→ 根因 → 改了什么（文件:行）→ 验证结果 → 遗留与风险。没有实测数字的归因一律写成"推测"，不要写成结论。

**提交口径**：本文件随代码一起提交（属于"影响后续排查的工程记录"，不算过程垃圾文档）。

## 2026-10-19 · 第三份真机日志读法纠正：那 15 次"退出"里有 14 次是应用内返回；探针升级到归因版

**现象**：用户导出第三份 `aiphone-perf-2026-10-19T07-15-54.json`（134 条），`build` = `2026-10-19.c（对局存储备忘 c80069d + 首帧窗口 e37cffc）` —— 与 dev 分支一致，这两个改动确实上了手机。用户口述"确实有优化，再看看还有没有问题"。

**读日志读出的第一件事（纠正上一轮的口径错误，下次别再踩）**：那份日志有 **15 条 `app-change {phase:"close-tap"}`，但 `app-change` 到 `null`（真的回到桌面）只有 1 条**。桌面壳的 `useEffect([activeApp])` 只在 `activeApp` 变化时才记，15 次里 14 次 App 还开着 —— 所以**它们是特调里"对局→大厅"的应用内返回，不是退出桌面**。原因在 `components/desktop-shell.tsx:3871` 的 `CLOSE_SEL = ".page-back-btn, [aria-label='返回'], [aria-label='关闭'], ..."`，而 `MixologyGame` 顶栏那颗返回键就是 `<button class="mix-icon-btn" aria-label="返回">`（`mixology-game.tsx:1051/1567`）。
推论：**第二份日志里我按"11 次退出"算出来的"退出后 628–697ms 尾巴"同样是应用内返回的成本，"退出 App 慢"这个命题到现在为止只被 1 个真实样本覆盖过。** 以后凡是读 close-tap 后面的长任务，必须先确认这条 close-tap 后面有没有跟一条 `app-change` 到 `null`。

**实测数据（同一份日志，`hidden:false` 全程可见，数字可信）**：
- 长任务最大 **2005ms**，`>1.8s` 只有 3 条（t=98634 / 113665 / 120196 附近）；上一份日志里进对局的长任务是 1338 / 2923 / 3029 / 4322 / 4328 / 5295 / 5610 / 6790 / 6989ms。15 次 close-tap 每次都必然先行进入过一场对局，所以这轮"打开对局"的量级确实从 6~7s 掉到 ≤2s。
- 每次 close-tap（应用内返回）后面稳定跟两条 **620–800ms** 长任务，`block` 合计 1042–1540ms。
- 唯一那次真退出：tap 117905 → `app-change null` 118047（提交 142ms）→ `exit-overlay 276ms` → **紧跟一条 2005ms 长任务**（起于提交后 141ms）。`exit-overlay` 这次记到了（上一份是 0 条），说明双 rAF 判定改对了；`veil-painted` 也有 2 条（637/700ms），遮罩在真机 WebView 上确实画得出来。
- kv 体积仍是 `mixology_sessions_v1` 14267kb / `ai_phone_api_logs_v1` 8123kb。

**开发机同数据实测（`localhost:3001`，31 场 / 2743 轮 / 14267kb；探针升级后自动记的，不是手搓脚本）**：
- 整包一次 `JSON.parse` = 63–84ms，`JSON.stringify` = 49–55ms，Dexie `put` 的同步段（结构化克隆）= 66–71ms → **一次整包读写 ≈ 180–210ms**。
- 进那场 193 轮（415 turns）对局：477ms；点应用内返回回大厅：260ms。开发机这两步里的整包读写占 180–210ms，手机同一步观测到 620–800ms×2 —— **量级和"整包读写 + 大厅重建"对得上，但两端比到比不齐（约 3.5~5 倍，机型不同不可互推），这一步只做定性对齐，不当中位数结论**。
- 关键新发现：**只是"进对局再退出来"，什么都没改，也会写一次 14MB 整包**（`bigjson op:str` + `idbwrite` 都出现在退出对局之后）。`readJson` 备忘把这次写之后的首次读也变成整包重解析（`writeJson` 必须删备忘，否则外部写入方会读到脏数据）。
- 另一条独立成本：`mixology-app.tsx:856` 的 `onBack={() => { setPlaying(null); refresh(); }}` —— `refresh()` 里 `loadMixSessions()` 又要读一次整包，而 `if (playing)` 是把整个大厅子树卸载再重挂。返回这一步同时付"重读 14MB"和"重建大厅"两份钱。

**根因结论**：剩下的卡不是"退出桌面卡"，而是**特调的整包存储被反复读写**：每回合落库、每次面板开合（`mixology-game.tsx:530` 的 `panelOpen`、:618 `panelBox`、:635 `state`）、每次进/出对局，都要把 14MB 序列化 + 写盘 + 再解析。14MB 里 99.2% 是 turns（把 31 场的 turns 全剥掉只剩 114kb），最大单场 1622kb/415 轮。

**改了什么（本次只动测量件和一处文案，不动存储结构）**：
1. `lib/perf-probe.ts`：探针升级到归因版 `2026-10-19.d`。三处新钩子 —— `long-animation-frame`（`loaf`：`sl` = 本帧第几 ms 才开始样式/布局，`-1` 表示整帧纯 JS；`rn` = 渲染阶段占掉多少 ms；`s` = 最贵的三段脚本的函数名+invoker）、`JSON.parse/stringify` 只在 ≥200KB 时记（`bigjson`：体积+耗时+调用栈前两帧）、`IDBObjectStore.prototype.put` 同步段（`idbwrite`）。探针自身序列化用 `_silent` 屏蔽，避免自记自。`MAX_EVENTS` 400→600（归因事件密度是原来的 3 倍以上）。IDB 钩子必须 `apply(this, args)` 原样转发 —— IDL 绑定按"实参个数"判断 key 有没有传，写成 `call(this, value, key)` 会把单参调用变成"显式传 undefined"，可能让 Dexie 的 in-line key 写法抛 DataError。

## 2026-10-19 · 第二份真机日志：进对局的"随轮数增长"那一块在首帧全量渲染；退出遮罩 500ms 定时器把测量整个吃掉

## 2026-10-19 · 进特调对局卡 6~7 秒：整包 14MB 被重复 parse，加 readJson 备忘

**现象**：用户真机日志（`aiphone-perf-2026-10-19T06-08-53.json`，122 条事件，build `2026-10-19.b`）里，`app-change mixology` 之后 1.3~2.5s 出现三条单条主线程长任务 **7568ms / 6527ms / 6328ms**（伴随同量级 `block` 事件 7675/6587/6468ms）。用户观感一致："主要问题集中在打开特调对局加载过久，聊天室打开还好"。

**真机日志同时证明退出已经不是问题**：环境 `{Android 10 / Chrome 154 WebView / dpr 3 / 360x804 / 8 cores / hidden:false}`（`hidden:false` 说明计时可信）；退出长任务 `exit-overlay` 聊天 309~355ms、特调 211~381ms；`note/veil-painted` 在点关闭后 403~569ms 出现 —— 上一条改动里的"遮罩在主线程被占住时到底画不画得出来"这个未验证项，**在真机 WebView 上已证实成立**。聊天打开长任务 155~271ms。kv 体积：`mixology_sessions_v1` 14267kb、`ai_phone_api_logs_v1` 8123kb、`custom_apps` 1389kb、`qa_api_logs` 1006kb、`mixology_cabinet` 534kb。

**开发机定位（同一份真实导入数据，`localhost:3001`，JSON.parse/stringify 挂钩记次数+调用栈 + longtask 观察器）**：

| 场景 | 改前 | 改后 |
|---|---|---|
| 进一场**只有 1 轮**的对局 | 长任务 818ms，其中 **22 次** >50kb 的 `JSON.parse` 共 756ms | 长任务 **116ms**，1 次 parse 73ms |
| 进 3 轮的对局 | 长任务 1007ms，22 次 parse 881ms | — |
| 进 193 轮的对局 | 长任务 3863ms，14 次 parse 共 958ms | 长任务 **2227~2734ms**，1 次 parse |
| 点「查看更早的 12 条」多挂 60 轮 | 长任务 129ms（≈2ms/轮） | — |

数据侧：整包 14267kb / 31 场 / 2743 轮，最大一场 1622kb（415 轮）。同一个同步任务里还出现 8 次 `loadMixCabinet`（534kb × 8 = 44ms）。

**根因**：`getMixSession(id)` 是 `loadMixSessions().find(...)`，也就是**取一场对局就要把 14MB 整串 `JSON.parse` 一遍**。进对局的那一个同步任务里它被调了 12~22 次（`useState` 初始化、`dialogueButtons` 初始化、`getState/getStore/charName` 这类每次渲染都跑的闭包、`MixSessionSwitcher` 的 `useState`），dev StrictMode 还会翻倍。所以卡时长里有一块**与轮数无关的固定地板**（实测 ~750ms），真机 CPU 慢数倍、按同样次数放大，正好落在用户看到的 6~7 秒；剩下的才是随轮数增长的部分。

**改了什么**：`lib/mixology/storage.ts:104-140` —— `readJson` 加 raw→已解析对象的模块内备忘 `jsonMemo`（上限 8 条，按插入顺序淘汰），`writeJson` 写完立即删条目，交给调用方的一律是 `freshCopy`（数组 `slice`、对象浅拷贝）。失效口径三条都写在代码注释里：① 命中要求 `hit.raw === kvGet(key)`，备份导入这类从外面覆写 key 的路径会换字符串引用，自动落回重新 parse；② 本模块一写就失效，避免"调用方先改缓存对象再写盘"或"改了没写"造成内存态与磁盘态分叉；③ 顶层引用每次都是新的，`setSession(getMixSession(id))` 依赖的重渲染语义不变。深层（turns/state/mechanismStore）改为共享引用，全仓 grep 确认对局写路径清一色 `{...session, turns}` / `turns.slice()`，唯一的 `turns.push`（`engine.ts:264`）操作的是当场新建对象。

**验证**：`tsc --noEmit` 通过；上表的进对局耗时（818→116ms、3863→2227ms，parse 14~22 次→1 次）；**写路径回归**：对局改名 → 直查 IndexedDB 确认 `name` 落库、31 场 / 2743 轮 / 14267kb 与改前基线逐项目视一致、界面列表同步显示新名（该次操作 2 次 stringify 56ms、4 次 parse，说明写后备忘正确失效）→ 再改名清回原状（重命名的"确定"对空名是禁用的，最后用直写 IDB 删掉 `name` 字段并刷新页面，标题回到 `charName · 配方名` 兜底显示，**测试痕迹已清除**）。

**遗留与风险（下一轮接着做之前先看这里）**：
1. **随轮数增长的那 ~2.2s（193 轮）没动**。窗口化渲染本身不贵（多挂 60 轮只 129ms），所以大头在挂载时的整局预处理 —— **推测**是装配/逐轮过滤，未实测证实；下次要在长任务内部做分段计时（给 `assembleFromSession`、逐轮 filter 应用、面板挂载分别打点）再动手。
2. **每轮出杯仍要整包 `JSON.stringify` 14MB**（实测 35~56ms，真机放大）+ 整包写盘。根治要把 sessions 拆成"每场一键 + 轻量索引"，牵动备份/导入/迁移，属于独立一次改动，别和这次混在一起。
3. **备忘会常驻一份 14MB 的已解析对象图**（直到该 key 下次写入才失效）—— 这是内存换时间。若真机出现内存压力或 OOM，优先把它降级成"仅当前任务内有效"（首次填充后用 `setTimeout(0)` 清条目），测得的收益基本不丢。

## 2026-10-19 · 退出等待约 5 秒：加返回遮罩 + 真机自记录性能探针（临时件）

**现象**：上一条改动把开发机的退出耗时从 540~600ms 压到 48~66ms，但用户真机实测仍要等约 5 秒，而且期间界面完全没反应 —— 分不清是卡住了还是在加载。

**关键事实**：开发机（Chrome / 20 核桌面 CPU）和手机 WebView 差一个量级，两端数字不可互推。没有端上数据就只能猜，所以这次先做测量件，不做无依据的优化。

**改了什么**：
1. `components/desktop-shell.tsx`：退出遮罩 `.app-exit-veil`（「正在返回桌面…」）。在 `pointerdown` 的**捕获阶段**挂 `is-on` class —— React 的 `onClick` 要等 pointerup 之后才跑，中间至少隔一帧，这样样式变更能在主线程被占住之前交给合成器；CSS 用 `transition: opacity 160ms linear 220ms`，**显形有 220ms 延迟**，快的设备一帧就画完桌面、遮罩来不及出现，不会闪。收回走双 rAF + 400ms 定时器兜底 + 10s 保险。
2. `lib/perf-probe.ts`（新）：真机自动记录，不需要控制台。记 boot 环境（UA/DPR/CPU 核数/deviceMemory/构建标识）、kv 各键体积、`navigator.storage.estimate()`、App 切换、所有 ≥80ms 的 longtask、主线程看门狗（setInterval 漂移 >400ms）、前后台切换。日志存 kv 键 `perf_probe_log_v1`，环形 400 条，刷新不丢。
3. `components/perf-probe-panel.tsx` + `styles/phone-shell.css` 的 `.perf-probe-*`：左下角「日志」浮钮 → 面板，可 导出文件 / 复制全文 / 刷新 / 清空。导出用 `lib/download-utils.ts` 的 blob 下载（和备份导出同一条已验证路径），复制走剪贴板 + `execCommand` 兜底。

**验证**：`tsc --noEmit` 通过；Fast Refresh 无报错；桌面/特调开合后遮罩正确显形并收回；面板能出摘要与原始事件；清空生效；日志跨刷新累积（boot=2）。
**未验证**：遮罩在"主线程真被占住 5 秒"时到底画不画得出来 —— 后台页 CSS 过渡不推进，开发机测不了。为此加了 `transitionend` 探针，真机日志里出现 `note/veil-painted` 才算证实；没出现就说明合成器这条路在 WebView 上不成立，得换成"先画遮罩再分帧做重活"的方案。**（2026-10-19 同日已由用户真机日志证实：`veil-painted` 出现在点关闭后 403~569ms，见最上方条目。）**

**踩到的坑（已修）**：
- 后台页 `setInterval` 被钳到 1s，看门狗把节流误报成 193 条 750ms "卡顿" → 现在 `document.hidden` 时直接不判定，摘要里也打印当前可见性。
- 只用双 rAF 收遮罩，在后台页 rAF 不触发 → 遮罩永久留在屏幕上（实测 `veilAfter: true`）→ 加 400ms 定时器兜底。
- 未水合时写日志会用空数组覆盖真日志 → `persist()` 前先 `isKvHydrated()`。

**拆除方式**：删 `lib/perf-probe.ts`、`components/perf-probe-panel.tsx`，去掉 `desktop-shell.tsx` 里 `perfProbe` / `PerfProbePanel` / `startPerfProbe` 的引用（遮罩本身可以留，只删探针调用），再删 `phone-shell.css` 的 `.perf-probe-*` 段落。`.app-exit-veil` 属于正常功能，不拆。

## 2026-10-19 · 退出 App 卡顿：桌面改为常驻挂载 + CSS 隐藏

**现象**：从任何 App 返回桌面都会卡住半秒以上，聊天、独家特调最明显。用户反馈"打开和关闭都卡"。

**测试条件（重要，换条件数字不可直接比）**：`npm run dev`（turbopack，localhost:3001），真实导入数据 —— 桌面 27 图标 / 8 组件 / 4 Dock；IndexedDB 实测 `AiPhoneKvDB` 72 条 / 33.9MB（其中 `mixology_sessions_v1` 14.3MB、`ai_phone_api_logs_v1` 16.3MB），主题库 169 资产 / 62.6MB（含 14.2MB 字体、2.7–4.6MB 图标皮肤），聊天库 77 消息 / 5 会话。探针：`tools/exit-lag-probe-chat-mix.js`（长任务 + 主线程阻塞 + DOM 就绪时刻 + `JSON.parse/stringify` 钩子；`tools/exit-lag-probe.js` 是桌面渲染 A/B 版。两者是本地诊断脚本，贴到浏览器控制台跑，不入库）。

**实测数据**：

| 场景 | 改造前 | 改造后 |
|---|---|---|
| 退出 App → 桌面图标挂好（前台，同数据） | 291–308ms（React 重挂）+ 245–289ms（首帧栅格化），单帧最长 246–343ms | 48–66ms，单帧最长 23–35ms |
| 退出 App（后台页 A/B，同一次会话内先后跑，条件一致） | DOM 392–467ms，长任务 392+404 / 466+418 | DOM 62–74ms，长任务 62–74 |
| 打开 聊天 | DOM 19–22ms，无长任务 | DOM 82–88ms，长任务 53ms |
| 打开 独家特调 | 长任务 69–75ms，2–3 次 >1MB `JSON.parse` | 长任务 96–120ms，2 次 >1MB `JSON.parse` |

**根因**：`components/desktop-shell.tsx` 里桌面与 App 正文互斥渲染（`{!activeApp ? <桌面> : <App>}`，Dock 同样 `!activeApp` 条件渲染），退出时桌面整棵树（30 多层 `backdrop-filter` 毛玻璃 + 图标皮肤图）被卸载后重新挂载，产生两条背靠背长任务。与是哪个 App 无关 —— 聊天和特调的退出数字一致。

**改了什么**：
- `components/desktop-shell.tsx`：桌面图标层 + 分页圆点包进 `.phone-desktop-layer`，Dock 的 `<footer>` 都改为常驻渲染；App 打开时给它们加 `inert` + `aria-hidden`。

**验证**：`tsc --noEmit` 通过；前台截图确认桌面（图标皮肤 / 组件 / 分页点 / Dock）与 App 全屏态均正常；退出后 `.phone-desktop-layer` 回到 `display:flex`、Dock 回到 `grid`；分页圆点切页 transform 正常；控制台无新增报错。

**遗留与风险（下次接着做之前先看这里）**：
1. **打开 App 变慢了约 40–60ms**：常驻后"挂 App + 把桌面从布局里摘掉"落在同一帧。收益（退出省 250–500ms）明显大于代价，但这条要继续优化，不能当作没发生。

3. **独家特调打开的 14MB 整包解析没动**：`lib/mixology/storage.ts` 的 `readJson` 对 `mixology_sessions_v1` 做整串 `JSON.parse`，`writeJson` 整串 `JSON.stringify`；`components/mixology/mixology-app.tsx:127` 在 `useState` 初始化里同步调 `loadMixSessions()`。要修得拆存储结构，属于独立一次改动。（已由同日最上方的 readJson 备忘条目部分解决：重复 parse 消除了，整包 stringify 仍在。）

## 排查这类问题时的固定坑（每次都要先确认）

- **空数据下测性能等于没测**。先量化数据规模（各库条数、字节数），把规模和计时一起写进结论。
- **页面在后台时帧率测不出来**。`document.hidden` 为真时 rAF 不触发、渲染任务被跳过，`setTimeout` 被钳到 ≥1s，长任务只剩脚本部分。要么把窗口切回前台，要么改用 MessageChannel 主线程阻塞采样，并且必须在结论里注明条件；**同一组 A/B 要在同一种可见性状态下跑**。
- **改了内联脚本先 `node --check` 再 build**，否则白屏会被误判成"数据丢了"。
- **自定义 App 沙盒**：`sticky` 定位、`backdrop-filter` 会触发 503；宿主 API 不支持 doc/docx 解析。
- **已安装 App 是 HTML 快照**：改源文件或重打 zip 不会自动生效，必须换包或重装并升 manifest 版本。
- **`saveMeta` 必须带 `customTemplates` 字段**（随想笔记），漏了会静默丢模板。
- **禁止在 `bind()` 里给条件渲染的元素绑事件**，要在 render 内绑或用事件委托。

# 改动记录（排查用）

**这份文档的用法**：动手改代码前先在这里搜一遍相关模块，看清"这里已经改过什么、为什么这么改、当时实测数字是多少"，避免把已经踩过的坑再踩一遍。每完成一个有实际影响的改动（性能、交互、数据结构、构建），在顶部追加一条。

**每条记录必须包含**：现象 → 实测数据（含测试条件与数据来源）→ 根因 → 改了什么（文件:行）→ 验证结果 → 遗留与风险。没有实测数字的归因一律写成"推测"，不要写成结论。

**提交口径**：本文件随代码一起提交（属于"影响后续排查的工程记录"，不算过程垃圾文档）。

## 2026-10-19 · 退出等待约 5 秒：加返回遮罩 + 真机自记录性能探针（临时件）

**现象**：上一条改动把开发机的退出耗时从 540~600ms 压到 48~66ms，但用户真机实测仍要等约 5 秒，而且期间界面完全没反应 —— 分不清是卡住了还是在加载。

**关键事实**：开发机（Chrome / 20 核桌面 CPU）和手机 WebView 差一个量级，两端数字不可互推。没有端上数据就只能猜，所以这次先做测量件，不做无依据的优化。

**改了什么**：
1. `components/desktop-shell.tsx`：退出遮罩 `.app-exit-veil`（「正在返回桌面…」）。在 `pointerdown` 的**捕获阶段**挂 `is-on` class —— React 的 `onClick` 要等 pointerup 之后才跑，中间至少隔一帧，这样样式变更能在主线程被占住之前交给合成器；CSS 用 `transition: opacity 160ms linear 220ms`，**显形有 220ms 延迟**，快的设备一帧就画完桌面、遮罩来不及出现，不会闪。收回走双 rAF + 400ms 定时器兜底 + 10s 保险。
2. `lib/perf-probe.ts`（新）：真机自动记录，不需要控制台。记 boot 环境（UA/DPR/CPU 核数/deviceMemory/构建标识）、kv 各键体积、`navigator.storage.estimate()`、App 切换、所有 ≥80ms 的 longtask、主线程看门狗（setInterval 漂移 >400ms）、前后台切换。日志存 kv 键 `perf_probe_log_v1`，环形 400 条，刷新不丢。
3. `components/perf-probe-panel.tsx` + `styles/phone-shell.css` 的 `.perf-probe-*`：左下角「日志」浮钮 → 面板，可 导出文件 / 复制全文 / 刷新 / 清空。导出用 `lib/download-utils.ts` 的 blob 下载（和备份导出同一条已验证路径），复制走剪贴板 + `execCommand` 兜底。

**验证**：`tsc --noEmit` 通过；Fast Refresh 无报错；桌面/特调开合后遮罩正确显形并收回；面板能出摘要与原始事件；清空生效；日志跨刷新累积（boot=2）。
**未验证**：遮罩在"主线程真被占住 5 秒"时到底画不画得出来 —— 后台页 CSS 过渡不推进，开发机测不了。为此加了 `transitionend` 探针，真机日志里出现 `note/veil-painted` 才算证实；没出现就说明合成器这条路在 WebView 上不成立，得换成"先画遮罩再分帧做重活"的方案。

**踩到的坑（已修）**：
- 后台页 `setInterval` 被钳到 1s，看门狗把节流误报成 193 条 750ms "卡顿" → 现在 `document.hidden` 时直接不判定，摘要里也打印当前可见性。
- 只用双 rAF 收遮罩，在后台页 rAF 不触发 → 遮罩永久留在屏幕上（实测 `veilAfter: true`）→ 加 400ms 定时器兜底。
- 未水合时写日志会用空数组覆盖真日志 → `persist()` 前先 `isKvHydrated()`。

**拆除方式**：删 `lib/perf-probe.ts`、`components/perf-probe-panel.tsx`，去掉 `desktop-shell.tsx` 里 `perfProbe` / `PerfProbePanel` / `startPerfProbe` 的引用（遮罩本身可以留，只删探针调用），再删 `phone-shell.css` 的 `.perf-probe-*` 段落。`.app-exit-veil` 属于正常功能，不拆。

## 2026-10-19 · 退出 App 卡顿：桌面改为常驻挂载 + CSS 隐藏

**现象**：从任何 App 返回桌面都会卡住半秒以上，聊天、独家特调最明显。用户反馈"打开和关闭都卡"。

**测试条件（重要，换条件数字不可直接比）**：`npm run dev`（turbopack，localhost:3001），真实导入数据 —— 桌面 27 图标 / 8 组件 / 4 Dock；IndexedDB 实测 `AiPhoneKvDB` 72 条 / 33.9MB（其中 `mixology_sessions_v1` 14.3MB、`ai_phone_api_logs_v1` 16.3MB），主题库 169 资产 / 62.6MB（含 14.2MB 字体、2.7–4.6MB 图标皮肤），聊天库 77 消息 / 5 会话。探针：`tools/exit-lag-probe-chat-mix.js`（长任务 + 主线程阻塞 + DOM 就绪时刻 + `JSON.parse/stringify` 钩子；`tools/exit-lag-probe.js` 是桌面渲染 A/B 版。两者是本地诊断脚本，贴到浏览器控制台跑，不入库）。

**实测数据**：

| 场景 | 改造前 | 改造后 |
|---|---|---|
| 退出 App → 桌面图标挂好（前台，同数据） | 291–308ms（React 重挂）+ 245–289ms（首帧栅格化），单帧最长 246–343ms | 48–66ms，单帧最长 23–35ms |
| 退出 App（后台页 A/B，同一次会话内先后跑，条件一致） | DOM 392–467ms，长任务 392+404 / 466+418 | DOM 62–74ms，长任务 62–74 |
| 打开 聊天 | DOM 19–22ms，无长任务 | DOM 82–88ms，长任务 53ms |
| 打开 独家特调 | 长任务 69–75ms，2–3 次 >1MB `JSON.parse` | 长任务 96–120ms，2 次 >1MB `JSON.parse` |

**根因**：`components/desktop-shell.tsx` 里桌面与 App 正文互斥渲染（`{!activeApp ? <桌面> : <App>}`，Dock 同样 `!activeApp` 条件渲染），退出时桌面整棵树（30 多层 `backdrop-filter` 毛玻璃 + 图标皮肤图）被卸载后重新挂载，产生两条背靠背长任务。与是哪个 App 无关 —— 聊天和特调的退出数字一致。

**改了什么**：
- `components/desktop-shell.tsx`：桌面图标层 + 分页圆点包进 `.phone-desktop-layer`，Dock 的 `<footer>` 都改为常驻渲染；App 打开时给它们加 `inert` + `aria-hidden`。
- `styles/phone-shell.css`：新增 `.phone-desktop-layer`（flex 列，占满工作区），并在 `.phone-workspace.app-open` / `.phone-shell.app-open-shell` 下对桌面层与 `.dock` 设 `display: none`。
- 同日的另一处：`.phone-wallpaper` 的 `transition: opacity 220ms ease` 改为 `none`。原因是壁纸淡入只在"返回桌面"时触发（打开 App 时被 `transition-duration: 0s !important` 瞬时隐藏），淡入的每一帧都会让全部毛玻璃重新采样背景。把淡入拉长到 2s 同样降到 27ms，证明成本是"逐帧重模糊"而非一次性栅格化。

**验证**：`tsc --noEmit` 通过；前台截图确认桌面（图标皮肤 / 组件 / 分页点 / Dock）与 App 全屏态均正常；退出后 `.phone-desktop-layer` 回到 `display:flex`、Dock 回到 `grid`；分页圆点切页 transform 正常；控制台无新增报错。

**遗留与风险（下次接着做之前先看这里）**：
1. **打开 App 变慢了约 40–60ms**：常驻后"挂 App + 把桌面从布局里摘掉"落在同一帧。收益（退出省 250–500ms）明显大于代价，但这条要继续优化，不能当作没发生。
2. **App 打开期间桌面树常驻**：桌面 state 变化会连带重渲染桌面子树。音乐浮层早已隔离（见 `desktop-shell.tsx` 中 `MusicShellOverlays` 上方注释），但后续若发现"App 内操作变卡"，第一个要怀疑的就是这里。
3. **独家特调打开的 14MB 整包解析没动**：`lib/mixology/storage.ts` 的 `readJson` 对 `mixology_sessions_v1` 做整串 `JSON.parse`，`writeJson` 整串 `JSON.stringify`；`components/mixology/mixology-app.tsx:127` 在 `useState` 初始化里同步调 `loadMixSessions()`。要修得拆存储结构，属于独立一次改动。
4. **聊天没复现打开卡顿**：本机聊天库只有 77 条消息，量级不够。代码侧同类隐患在 `lib/chat-storage.ts:997` `hydrateChatStorage()`：`chatDb.messages.toArray()` 全量取行（含内联 base64 附件，未剥离），随后 `refreshSessionPreviewMetadata` 对每个会话全量排序，O(会话数 × 消息数 log n)。用户真实数据更大时才会成为主角。
5. **`ai_phone_api_logs_v1` 16.3MB**：`lib/api-log-store.ts` 每发一次 LLM 请求就整包 parse + stringify（`_loadLogs:50` / `_saveLogs:58`），调用点 `chat-engine.ts:922` 等。这是独立的第三个问题。

## 排查这类问题时的固定坑（每次都要先确认）

- **空数据下测性能等于没测**。先量化数据规模（各库条数、字节数），把规模和计时一起写进结论。
- **页面在后台时帧率测不出来**。`document.hidden` 为真时 rAF 不触发、渲染任务被跳过，`setTimeout` 被钳到 ≥1s，长任务只剩脚本部分。要么把窗口切回前台，要么改用 MessageChannel 主线程阻塞采样，并且必须在结论里注明条件；**同一组 A/B 要在同一种可见性状态下跑**。
- **改了内联脚本先 `node --check` 再 build**，否则白屏会被误判成"数据丢了"。
- **自定义 App 沙盒**：`sticky` 定位、`backdrop-filter` 会触发 503；宿主 API 不支持 doc/docx 解析。
- **已安装 App 是 HTML 快照**：改源文件或重打 zip 不会自动生效，必须换包或重装并升 manifest 版本。
- **`saveMeta` 必须带 `customTemplates` 字段**（随想笔记），漏了会静默丢模板。
- **禁止在 `bind()` 里给条件渲染的元素绑事件**，要在 render 内绑或用事件委托。
